# Usage design: one experience across all terminal tools

Status: decided (user, 2026-10-31). Done: `ui::keys` (engine, which-key popup), the `files` migration, the palette (`Space Space`) and `?` help; still to do: the other tools, the shared leader setting and the Nix key config. Applies to every tool built so far (`files`, `pick`, `pv` where interactive, `git-ui`, `git-panel`, the diagnostics panel, the helix docks and popups) and to every future tool.

The look is shared through the `ui` crate. This document is the same idea for behaviour: what keys do, how actions are found, how a tool is embedded.

## Principles

1. **One grammar.** The same key means the same verb in every tool. A tool never invents a different key for a verb in the table below.
2. **Discoverable, not memorized.** Every action can be found by name (palette) and by key (`?`, the leader menu). Hints shown on screen are generated from the same data, so they cannot go stale.
3. **Everything shared, nothing copied.** One engine (`ui::keys`) does dispatch, the leader menu, the palette, help, hints and user config. A tool only declares its actions and implements them.
4. **Configurable once.** Keys come from one user config (generated by Nix, like the color tokens). Rebinding an action rebinds it everywhere it appears.
5. **Embeddable.** When a tool runs inside a host (a helix dock), the host's leader always reaches the host unless the tool is taking typed text, and keys the tool does not claim go to the host.
6. **Safe by default.** Destructive actions ask first (`y`/`n`) or go to the trash; `Esc` always backs out.

## The leader and the palette

- **Space is the leader in every tool** (setting `dotfiles.editor.leader` now, to become one shared `ui.keys.leader`). It opens the same which-key popup everywhere, listing the tool's grouped actions.
- **`Space Space` opens the command palette** in every tool: a fuzzy list (the shared `pick`) of all actions of the tool, with name, description and key. Helix keeps `:` as its own command line.
- **`?` shows the keys of the current pane**, from the registry.
- Single-letter keys are for the verbs below. Everything tool-specific that is not a verb goes under the leader menu, so tools cannot clash with each other.

Examples (target layout):

```
files  Space ▸  f find   g grep   b bookmarks   v view ▸ (columns, preview, properties, hidden)
                t tabs   o open with   B bulk rename   ? keys   Space palette
git    Space ▸  c commit   p push/pull ▸   b branches   z stash ▸   r rebase ▸   ? keys   Space palette
```

## Shared keys and verbs

| Key | Meaning | Where |
|---|---|---|
| `j` `k` / arrows | move | all lists |
| `g` `G`, `ctrl-d` `ctrl-u` | top / bottom, half page (also scrolls previews) | all |
| `Enter` | the primary action: open, accept, check out | all |
| `l` / `h` | go in or expand / go out or collapse | files, pick, branches |
| `Tab` | mark for multi-select | files, pick, git files |
| `/` | filter this list (the shared picker) | all lists |
| `a` | add / new | files, branches, stashes |
| `d` / `D` | delete or drop, asks first / force | all |
| `r` | rename | files, branches |
| `y` `x` `p` | copy, cut, paste | files |
| `s` / `u` | stage or switch on / undo | git |
| `1`-`9` | jump to a pane or tab | git-ui, files tabs |
| `Esc` | back out one level: prompt, confirmation, focus to the list, clear marks | all |
| `q` | close the tool | all |
| `?` | keys of this pane | all |
| `Space`, `Space Space` | leader menu, palette | all |

## Machine interface (every standalone tool)

- Same flags where they apply: `--chooser-file`, `--cwd-file`, `--no-git`, `--no-preview`.
- Same exit codes: 0 selected or done, 1 nothing matched, 2 usage or error, 130 cancelled.
- Draw on `/dev/tty` so stdin and stdout stay free for pipes; popup inside zellij.

## How it is built (`ui::keys`)

- A table of actions per tool: id, name, description, group, default keys, mode (normal, prompt, confirm).
- The engine provides dispatch, the which-key popup, the palette, `?`, status hints and clash detection (a registry test fails if two actions of one tool share a key or if an action has no name or description).
- User keys come from `dotfiles.keys.<tool>.<action>` in Nix, written to a file the engine reads at startup.
- Helix's existing leader menu moves onto the same registry so it matches the rest.

## Checklist for a new tool

1. Declare its actions in the registry (verbs from the table first, the rest under the leader).
2. Has a palette entry and a `?` entry for every action.
3. Esc and q behave as above; destructive actions confirm.
4. Passes the host's leader through when embedded; reports typing state.
5. Uses `ui` for list rows, prompts, panes and icons.
6. Standard flags and exit codes if it is a standalone tool.

## Rollout

1. `ui::keys` (engine, leader popup) and migrate `files` first (most keys, the missing leader).
2. Palette and `?`, then `pick`, `git-ui`, `git-panel`, diagnostics.
3. The Nix key config.
4. Helix's leader menu on the registry.

## Known clashes to resolve in the migration

- `files`: Space toggles a folder (use Enter, `l`, `h`), `c` cycles columns, `m` bookmarks, `S` greps, `i` toggles properties: these become leader entries.
- `git-ui`: `c` commits in the Files pane (stays: a verb in git), `M` merges (leader).
